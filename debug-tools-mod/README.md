# Debug Tools (`debug_tools`)

Отладочные команды для проверки сборки. Только ручная установка: `tfc addons install debug_tools`. Нужны права
оператора (2), игрокам не нужен. Логика только на сервере, поэтому ставится туда, где работает мир: хосту в папку игры
или на выделенный сервер.

| Команда                                          | Что делает                                                                           |
| ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `/tfcdebug vein list [слово]`                    | все жилы из реестра: редкость, высоты; зелёные есть в биоме под игроком              |
| `/tfcdebug vein find <жила> [радиус] [сколько]`  | ближайшие центры жилы по сиду мира, чанки не генерируются. Координаты кликабельны    |
| `/tfcdebug vein check <жила> [радиус] [сколько]` | генерирует чанки у центров в подходящем биоме и считает настоящую руду               |
| `/tfcdebug ore <блок> [радиус]`                  | сколько блока в квадрате вокруг игрока, высоты, пример координат; чанки генерируются |

Радиус — в чанках: у жил 256 по умолчанию (до 1000), у `ore` 4 (до 32). `check` и `ore` работают по одному чанку или
центру за тик и пишут итог в чат и в лог строками `[tfcdebug]`.

`check` и `ore` меняют мир: генерируют чанки. Только в копии мира. Жилы появляются лишь в чанках, сгенерированных
после того, как жила попала в сборку: в уже посещённых чанках `check` покажет 0.

## Как это работает

Центр жилы TFC зависит только от сида мира и номера чанка: `VeinFeature.getVeinsAtChunk` (байткод TFC 4.2.9). Будет ли
там руда, решают биом (`BiomeGenerationSettings.hasFeature`, у TFC жилы идут через тег `tfc:in_biome/veins`) и порода:
жила заменяет только блоки из своего списка `blocks`, поэтому центр в неподходящей породе даёт 0 руды. `find` этого не
знает, `check` показывает породу в центре.

## Аудит регистрации Create (dev #312)

`./libs.sh && ./gradlew devtestJar` собирает отдельный `debug-tools-1.0.0-devtest.jar`. Основной
`debug-tools-1.0.0.jar` не содержит диагностику. Проверочный jar ставится только в изолированный профиль стенда,
где уже есть Create и Registrate; публиковать его игрокам не нужно.

По байткоду Create 6.0.10, Registrate 1.3.0+67 и NeoForge 21.1.251:

- Create запускает `AllAdvancements.register()` при `RegisterEvent` реестра триггеров.
- Иконка достижения немедленно разрешает `AllItems.EXTENDO_GRIP` через `ItemProviderEntry.asStack()`.
- `AbstractRegistrate.accept()` записывает регистрации в обычный `HashBasedTable`, не защищённый от параллельной записи.

Mixin только наблюдает таблицу: печатает первые стеки потоков-писателей, перекрытия `accept`, наличие
`extendo_grip` перед триггерами и сверяет захваченные имена с таблицей перед регистрацией и с реестром после неё.
`REGISTRATE AUDIT LOST` останавливает прогон до скрытия потерянной записи последующим NPE;
`REGISTRATE AUDIT UNBOUND` означает, что захваченная запись осталась несвязанной после `onRegister`.
Он не синхронизирует исходный `put` и не исправляет регистрацию. Собственные счётчики потокобезопасны.

Успешный старт без потерь не доказывает устранение редкого сбоя. Подтверждение параллельной потери требует
`OVERLAP` вместе с `LOST` на настоящем профиле либо другого воспроизведения с установленным инициатором.

Проверка 26.11.2026: аудит `20261126-175636-ad19` прошёл с JAR SHA256
`0d63deaa1a90e4e96f66e85b7ac84b4cdaa5376b7ef0fb069fac3c9b1d086583`.
Зафиксированы два разных threadId: Create Deco вызывает `AllItems.<clinit>`, Aeronautics — `AllBlocks.<clinit>`.
Есть перекрытие `accept()` для `minecraft:item` и других реестров общей Create Registrate. В этом запуске
все 699 предметов и 643 блока зарегистрировались, `extendoBound=true`: исходная потеря `extendo_grip` не повторена.

Парный аудит `20261126-191010-c1fb` с тем же SHA и единственным overlay `config/fml.toml` (`maxThreads=1`)
прошёл: `debug.log` подтверждает `Using 1 threads for parallel mod-loading`, перекрытий нет, 699/699 предметов
и 643/643 блока связаны, `extendoBound=true`, меню за 122 с. Пул может менять/добавлять потоки при ожиданиях:
зафиксированы два threadId последовательно, поэтому количество физических потоков не приравнивается к `maxThreads`.
Параметр ограничивает целевой параллелизм ForkJoinPool, но не даёт строгой взаимной блокировки.
Адресная защита стенда находится в `tfc-plans/scripts/client-stand/RegistrateGuard.java`: отдельный Java agent
оборачивает таблицу `registrations` в `Tables.synchronizedTable` до первого использования. Он проверяет точную
структуру конструктора и при несовпадении завершает тестовую JVM кодом 86. Основной JAR Debug Tools и профиль игроков
не получают эту защиту. Диагностический аудит дополнительно печатает фактический класс таблицы (`tableClass`).
